## 记录共同工作的起点

为翻译批次记录上游分支、目标提交、中文分支和覆盖目录。多人参与时，记录每人的范围以及共用片段的维护位置。发现同一术语在多个页面出现时，先查项目术语表，再决定在哪一批次更新。

把能影响读者的差异单独写清。例如，中文页需要保留一段本地部署说明时，记录加入原因、适用版本和负责更新的页面。上游发布后可以据此判断该补充是否仍适用。

## 给接手的人可查证的信息

| 交接项   | 建议记录                               |
| -------- | -------------------------------------- |
| 翻译基准 | 原文仓库、提交和文档目录               |
| 覆盖进度 | 已更新的章节、待补章节和入口           |
| 术语约定 | 已确定译名、变更来源和使用范围         |
| 验证状态 | 已预览的平台、已执行的示例和待确认行为 |

版本说明、配置参考和示例之间有依赖时，说明修改次序。例如，先更新配置参考中的默认值，再检查教程和故障排查中引用旧值的段落。

## 安排后续更新

按读者影响安排优先级。会导致操作失败的步骤、已失效的命令和版本误导优先。纯措辞修订可以结合后续审阅整理。更新后用[上游差异核对](/docs/translation/upstream-sync)记录本批次的终点，并把剩余问题留在可追踪的位置。
