## 先复查本次的目标和范围

阅读拉取请求标题、描述和关联议题，找出读者任务、目标版本及改变的行为。修改跨页时先看导航和受影响入口，再展开差异。生成文件变化时找到原始输入，确认修改来自可维护的位置。

把改动标题、默认值、操作或权限的段落作为第一轮关注点。译文 PR 需要同版本原文和修改范围，可以按[审阅译文](/docs/translation/review)对照。

## 走一遍读者路径

1. 从导航或链接打开预览页，检查标题、摘要和前置条件。
2. 从文中声明的起点操作，核对复制命令、依赖和预期输出。
3. 打开被新增、移动或改名的页面和锚点，检查搜索入口。
4. 在较窄宽度读取表格、截图和提示框，必要时用键盘切换控制。

读者会进入的版本、平台和配置组合应由改动范围决定。记录确实走过的路径和仍需项目维护者确认的条件。对技术声明，能以源码、测试或运行结果定位时，提供对应证据。

## 用可采取的动作描述意见

例如，“这个步骤在仓库根目录会找不到 `./fixtures`。请写明先进入示例目录，并复查相邻代码块的运行位置。”反馈指向相应行，并说明问题怎样影响完成任务。提出多种合理写法时，给出选用条件。

回看新版本时复验受影响步骤。若可以通过，并列出已验证的环境或示例。需要进一步调整的细节可按[审阅反馈示例](/docs/reviewing/feedback-examples)组织。
